# PSAI 设计与验收约定

## 目标与边界

本机优先，兼容可调用 shell 的 agent 和支持 MCP 的 harness。agent 使用自己的模型与推理流程，游戏内桥接只负责观察和动作。

首版从用户手动启动并载入的独立测试存档开始，以基础开局、普通难度的营业日作为验收基线。机器生产链、全部夜间地点和特殊剧情交互列入后续扩展。遇到超出已支持范围的动作，应返回具体限制并等待 agent 决策。

## 架构

### 按交互机制扩展

以原版程序集的交互入口为适配单位。agent 通过说明、operations 和 use_conditions 发现当前用途，具体配方、材料与经营流程由模型结合状态选择。液体灌装作为物品间加工的代表性验收，样本测试用于检验机制覆盖。

- 库存与容器使用 GameInventory、PixelWindow、正常空位搜索与内容窗口入口，读取当前可见槽位及嵌套关系。总容量查询读取候选容器本体格形，内容继续遵循窗口可见性。
- 单件物品操作使用原版 May/CanActivate、May/CanToggle 与对应动作。物品间作用使用 MayTarget、CanTarget、Target，覆盖遵循此机制的工具、升级及加工。operations 按需查询，避免每次观察枚举所有物品配对。
- 机器布局统一遍历 Row、Panel、Intake、Stack 和当前 Tabs 页，读取槽位与文字。控件覆盖普通按钮、单选、滑块和范围滑块，遵循可见性、禁用状态、边界与原版回调。长按控件仍需单独验证。
- Unity UI 读取实际注册面板中的 TMP 与旧版 Text、按钮及禁用状态。对话和响应选择使用原版选项、说明、条件与激活入口，支持物品提交类操作的发现。
- 独立纸面板集中登记正常读取与关闭入口，名片仅在打开时提供其关联的原版号码。外出与电话保留转场和手动对白的状态观察。
- 特殊鉴定小游戏、精确摆放与旋转、配方快捷选择和其他独立控件按机制继续登记待验收。当前通用接口对同类系统提供复用能力，具体机器是否闭环通过仍按实机证据记录。

默认以结构化信息和文字为先。用户本轮明确允许读取当前顾客的独立内部通缉身份，输出原字段及来源，并与其他犯罪线索区分。其余观察继续按当前接口约定的可见范围读取。

Agent → CLI 或 MCP → 本机消息目录 → 原生模组 → 游戏正常行为 → 结构化结果。

- 游戏内 C# 使用 `netstandard2.1`，引用玩家本机的游戏程序集。
- CLI 和 MCP 采用 TypeScript / Node.js 24，复用传输与命令处理代码。
- 模组 ID 为 `psai`，使用 `ModHelper` 管理 `ModData/psai/` 内的 JSON 文件。
- 模组首先争取保持空 `<Capabilities />`。每次新增桥接行为后重新运行游戏扫描器，优先使用官方辅助方法和可检查的游戏类型访问。
- 不同游戏阶段的对象在载入后获取，离开存档后释放。Unity 对象访问、快照和动作统一在主线程完成。

## 工具与协议初稿

工具包括 `status`、`observe`、`inspect(target, detail)`、`actions`、`act` 和 `result(command_id)`。

- `status` 返回连接、协议版本、游戏版本和支持的功能。
- `observe` 返回阶段、已显示的对话、交易概况和状态版本，库存默认摘要。
- `inspect` 按需读取玩家已具备观察条件的具体细节。
- `actions` 返回当前支持的合法操作，执行时再次检查前置条件。
- `act` 每次执行一个改变游戏状态的动作，返回结果或 pending 状态。
- `result` 查询同一命令的最终结果。

命令携带 `session_id`、`command_id`、`expected_revision`、动作名称和参数。状态版本随与决策有关的状态变化递增，对象 ID 只在对应游戏会话内有效。

外部写入命令时采用同目录临时文件和原子重命名。游戏内通过官方辅助接口读写文件，每个命令使用独立文件。读取端对不完整 JSON 重试，验证会话 ID 和命令 ID。所有改变状态的动作串行执行。

同一会话内重复命令返回已记录结果，相同 ID 携带不同参数则拒绝。超时后查询原命令。若进程在动作执行与结果写入之间退出，下一次连接明确报告结果不确定，由 agent 重新观察，不自动重放。

## 玩家可见信息

采用查询制鉴定。`inspect` 可以描述磨损、封口、标签日期、厂号、配料等玩家可观察事实，每项输出都要对应合法的观察条件。

- 直接读取外观数据前核对游戏实际显示规则，包括被遮盖或尚未揭示的部分。
- 原始标签中的 CORRECT、COUNTERFEIT 等语义不得进入观察输出。图案用中性描述，难以转换时导出当前可见的局部图像。
- 真伪、正确估价和未来事件继续遵循玩家观察条件。当前顾客的独立通缉身份按本轮用户授权单独返回，标明内部字段来源。
- 检测设备的结果通过正常检查动作获取，核对设备、所有权、消耗和解锁条件。
- 游戏内指南和已获得文件提供规则信息，由 agent 结合观察自行判断。

本机静态检查已发现机械手、肋明治、燃料界面使用具体特征数据。映射仍需与实际画面和可见条件逐项验证。

## 动作与节奏

优先复用正常 UI 操作所走的动作入口及其条件检查，避免直接改金钱、所有权或交易结果。物品移动需要检查容器限制、格子容量、旋转、归属和当前交互锁。

动作完成以游戏状态变化和动画结束为依据。返回 `busy` 或 `pending` 时限制新动作，保留轮询能力。正常对话采用手动推进，关闭自动呼叫下一位顾客。选项修改前记录原值，结束控制时恢复。

不对模型推理设实时响应要求。验证等待 30 秒、120 秒和后台运行，记录对话、顾客和事件的状态变化。若发现例外计时，明确标记相应能力，在适配完成前限制该交互。

## 实施顺序与验收

1. 游戏内加载骨架，建立会话、只读状态与 JSON 往返，记录一次可靠快照。
2. 验证叫号或单步对话闭环，增加状态版本、动作条件、去重和执行结果查询。
3. 覆盖库存移动、报价、成交、确认取消、关店、睡眠、日结和次日状态。
4. 接入 CLI 与 MCP，完善按需鉴定、图像补充及兼容检查。

验收需要完成一个正常营业日，包含至少一笔正常交易，并覆盖余额不足、库存满、不可选选项、过期对象、过期状态、重复成交请求、超时和重启。CLI 与 MCP 对相同命令返回一致语义。核对 fair-play 信息边界和卸载后的存档可载入性。

测试以独立存档为对象。开始前核对已启用的第三方模组，先完成可归因的基线，再补充兼容测试。验收记录包含游戏构建、模组提交和具体结果。
